**Architecture Guard** is a technology-agnostic **SDD Tools Orchestration layer** for AI-assisted engineering.

AI agents (like Claude Code, Gemini, and OpenCode) are incredibly fast but often create architectural drift, duplicate business logic, and ignore established patterns. Architecture Guard solves this by wrapping their actions in structured, governed workflows. It automatically forces agents to check historical memory, validate plans against architecture rules, and apply pragmatic engineering constraints before writing any code.

It orchestrates the full delivery path—from discovery and specification through planning, implementation, and verification—while adapting to the project's existing SDD tool. It works with **OpenSpec**, **Spec Kit**, or a generic Markdown workflow without replacing them.

## 🌟 Core Features: Built for AI Engineering

Architecture Guard doesn't just manage files; it actively constraints AI behavior using proven engineering practices:

* **OpenSpec & Spec Kit Governance:** Detects the active SDD tool and applies the matching artifact paths, commands, and gap fills.
* **Jira Story Scope:** Discovery proposes related stories for you to accept, and specifications record the accepted set for later scope checks. Jira access is read-only during discovery and review. [Story scope guide →](docs/workflows.md#story-scope-check-jira)
* **Governance Suggestions:** Discovery can propose rule or workflow changes with supporting evidence; applying them requires a separately approved edit. [Discovery workflow →](docs/workflows.md#governed-discovery-workflow)
* **Ponytail Core:** Applies one shared decision ladder across discovery, planning, tasks, implementation, and review. Includes root-cause caller tracing, a safety floor, and runnable checks for non-trivial logic. *(Inspired by the [Ponytail Pragmatism Skill](https://github.com/DietrichGebert/ponytail))*
* **DRY Cleanup Guidance:** Prevents agents from blindly copying code. It helps find duplicated business logic, validation, DTO mapping, and orchestration, turning them into small refactor tasks instead of silent drift.
* **Flash-Mem Context Injection:** Automatically queries [Flash-Mem](https://github.com/DyanGalih/flash-mem) first to inject historical architectural decisions before the AI generates any new plans or specs.
* **Repository Hygiene Guard:** Automatically detects stray `*-copy.ts` drafts, orphaned code, and debug artifacts generated by AI before they hit your main branch. [Learn more →](docs/repository-hygiene.md)
* **SonarLint Code Quality Bundle:** Ships 37 architecture-relevant rules across Java, JavaScript, TypeScript, Python, and PHP (derived from [SonarSource](https://rules.sonarsource.com)) to catch brain overload, cyclomatic/cognitive complexity, coupling, and boundary cast drift during implementation reviews. [Sonar rules guide →](sonar-rules/README.md)
* **Multi-Host Parallel Agent Teams:** Coordinates specialist subagents (`analyst_reviewer`, `code_reviewer`, `implementor_be`, `implementor_fe`, `implementor_test`, `implementor_e2e`) across Claude Code, OpenAI Codex, Google Antigravity (`agy`), and OpenCode with tiered workspace isolation. [Team roles guide →](docs/standalone-usage.md#team-roles)

## 🚀 Installation & Setup

Architecture Guard is published on npm as a standalone SDD orchestration tool and installer for agent-native workflows. The simplest way to use it is directly via `npx`:

```bash
npx architecture-guard
```

Or, if you prefer to install it globally on your machine:

```bash
npm install -g architecture-guard
architecture-guard
```

To update a globally installed CLI explicitly, run `architecture-guard update` (or `architecture-guard self-update`).

The installer launches a setup wizard that asks you to select:
1. **AI agent(s)** — OpenCode, Claude Code, Gemini CLI, etc.
2. **SDD tool** — Spec Kit, OpenSpec, a generic Markdown workflow, or any other SDD tool through a [custom adapter](ADAPTERS.md#custom-adapters).
   The **code host** (GitHub, GitLab, Bitbucket, Azure DevOps, or plain git) is auto-detected from the `origin` remote for pull-request work; override it with `--forge`. See [FORGES.md](FORGES.md).
3.  **Governed workflows** — Pick the orchestration and governance workflows you need.

It installs the necessary command files directly into the agent command or skill directory. The installer uses `@inquirer/prompts`; lean prompts require a callable `architecture-guard` CLI for resource resolution and CLI-backed hygiene, while `--vendor` copies static engine resources locally and avoids bundled-resource lookup for those assets.

## 🧭 The Governed Workflows

Instead of letting AI agents run wild, Architecture Guard provides structured entry points that guide them from idea to implementation safely:

| Workflow Command | When To Use | What It Does |
| :--- | :--- | :--- |
| **`ag-governed-discover`**<br>*(or `/speckit.architecture-guard.ag-governed-discover`)* | Idea-stage | Shapes a rough request into a spec-ready direction *before* formal specification. |
| **`ag-governed-delivery`**<br>*(or `/speckit.architecture-guard.ag-governed-delivery`)* | Delivery stage | Resumes governed delivery from an active specification through plan and task generation, with optional memory context, security and architecture gates, task reconciliation, analysis, and an automatic artifact review loop that repairs findings until a review pass is clean. |
| **`ag-governed-delivery-team`**<br>*(or `/speckit.architecture-guard.ag-governed-delivery-team`)* | Team delivery | Creates stakeholder-approved User Stories (single-story `user-stories/<feature>.md` or decomposed parent + per-item child stories `user-stories/<feature>/<story-id>.md`) and optional `.architecture-guard/backlog.yml` breakdowns, with optional one-way sync to Jira (Epic + Stories) or GitHub Issues before planning and task generation. |
| **`ag-governed-archive`**<br>*(or `/speckit.architecture-guard.ag-governed-archive`)* | Finalization | Archives a completed feature after verification, with explicit approval for changelog, memory, Git, and cleanup actions. |
| **`ag-governed-implement`**<br>*(or `/speckit.architecture-guard.ag-governed-implement`)* | Implementation | Executes the generated tasks while strictly following the plan and architecture rules. |
| **`ag-governed-backlog`** | Several stories, bugs, and tasks at once | Reads a prioritized backlog from Jira, Beads, or a local `backlog.yml`, groups related items, and delivers code-writing groups as separate changes and pull requests; research groups run discovery only. You approve the queue, specifications, implementation scope, and publishing; blocked groups are parked. [Backlog queue →](docs/workflows.md#backlog-queue) |
| **`ag-e2e-testing`** | Testing a feature end to end | Decides from the spec whether the feature needs end-to-end tests. If it does, it designs scenarios from the acceptance criteria and writes them with Playwright: browser tests for UI journeys, API-only tests for API scope. If the spec isn't end-to-end, it skips them and names the lower-level tests to write instead. |
| **`ag-review-pr`** | Reviewing someone else's pull request | Fetches the pull request from your code host (GitHub, GitLab, Bitbucket, Azure DevOps, or plain git), reviews it against your architecture, security, and hygiene rules, runs Security Review (`sr-branch`) when that separate tool is installed, and drafts a comment-only review that is posted only when you choose. When no finding is blocking, you can instead approve it with comments asking the author to address the findings before merging. |
| **`ag-pr-feedback`** | Feedback on your own pull request | Triages unresolved review threads and failing checks, applies the fixes you approve, drafts replies, and lets you choose to reply only or reply and resolve. |
| **`ag-pr-queue`** | All your pull-request work in one command | Scans the repository's open pull requests, or takes a list, then runs `ag-pr-feedback` on your unapproved ones and `ag-review-pr` on your team's. It prepares every draft and triage first, then you decide them together at batched gates. Nothing is posted, pushed, or approved without your explicit choice. |

*(Note: Granular commands like `ag-governed-spec`, `ag-governed-plan`, and `ag-governed-tasks` are still available if you want manual control. See the [Workflow Guide](docs/workflows.md).)*

### Suggested Feature Delivery Flow

```text
/ag-governed-discover (optional, to brainstorm an idea)
  → /ag-governed-spec (creates and clarifies the specification)
  → /ag-governed-delivery (generates or reconciles the plan and tasks)
  → /ag-governed-implement (writes the code)
  → /ag-verify base=main (checks for unapproved drift and runs the same change checks as the pull-request review)
```

### Suggested Pull Request Flow

```text
/ag-review-pr <number or URL>   (reviewing a teammate's pull request)
/ag-pr-feedback                 (working through feedback on your own pull request)
/ag-pr-queue                    (all of it in one command: feedback on your open pull requests, reviews for your team's)
```

Both skills reach your code host through a [forge adapter](FORGES.md): a registered MCP server for the host, then its CLI (`gh`, `glab`, `az`), then plain git. Nothing is posted, pushed, or resolved without your approval.

## ⚙️ Design Philosophy

- **Non-blocking by default**: violations become refactor tasks unless a rule is explicitly marked blocking.
- **Reviewable in Git**: the rules live in markdown files, not hidden state.
- **Architecture first**: orchestration keeps boundaries, ownership, and drift visible across the delivery lifecycle.
- **Ponytail Core**: one shared ladder prevents both over-building and unsafe under-building across every delivery phase.

## 🔄 Spec Kit Compatibility

The standalone orchestrator is the primary experience, and all new features ship there. The legacy Spec Kit extension (`extension.yml` installation) remains available for existing Spec Kit users with limited support: it receives safety and breakage fixes only, not new features. New Spec Kit projects should use the standalone installer with `--framework spec-kit`.

If your project is already centered on Spec Kit, you can continue installing Architecture Guard as a native Spec Kit extension. See the [Spec Kit Integration Guide](SPECKIT-INTEGRATION.md).

### Multi-host Agent Teams (Claude, Codex, Antigravity, OpenCode)

Install skills and optional native team roles with `architecture-guard init . --yes --agent <host> --<host>-agents` (supports `claude` with `--claude-agent-teams`, `codex` with `--codex-agents`, `antigravity` with `--agy-agents`, and `opencode` with `--opencode-agents`). Interactive CLI setup asks a unified multi-select across all selected team-role hosts, interviews for custom rosters/models, and configures auto-activation (`agent_teams.activation: auto | ask | manual`) and workspace isolation (`agent_teams.isolation: auto | worktree | shared`) in `.architecture-guard/config.yml`. Refresh roles anytime with `architecture-guard sync-team-roles --agent <host>`. Profiles and role files remain separate per host (`.codex/agents/*.toml`, `.agents/agents/*.md`, `.opencode/agents/*.md`, `.claude/agents/*.md`).

Sequential execution is the default when unconfigured. Coordinated implementation activates automatically when configured with `agent_teams.activation: auto` or when explicitly selected for the run, dispatching parallel read-only review passes (`Analyst Reviewer` || Plan/Task `Security Review`, and `Code Reviewer` || Implementation `Security Review` || `E2E`) and concurrent writer implementors (`[BE]`, `[FE]`, `[TEST]`, `[E2E]`). Concurrent writers run with tiered workspace isolation: host-native workspace sharing (`agy` `share`) or per-role Git worktrees (`.git/ag-worktrees/agteam-<role>`) in the owning repository for shared-tree hosts (`codex`, `opencode`). Lead sessions reconcile worktrees, halt on conflicts, and prune temporary worktrees before hygiene checks. Parent permissions apply; Codex and OpenCode role files cannot override sandbox, approval, or MCP settings. Unsupported required restrictions prevent role activation.

Shared contracts govern delegation, complete handoffs, current-context reuse, and exact-scope approval reuse. Distinct human gates and external effects retain approval. See [setup and permission details](docs/standalone-usage.md#team-roles) and [execution policy](docs/governance-model.md#host-agent-execution). Fixture tests do not prove runtime host enforcement; unavailable host/security checks are reported explicitly.

Resource overrides and generic/OpenSpec archive paths must not contain symbolic links below the workspace root; the CLI rejects them to prevent paths escaping the workspace. These checks assume the workspace is not concurrently modified by an untrusted process while the CLI runs.

## 🙏 Credits, Inspirations & Ecosystem References

Architecture Guard is built alongside and inspired by open-source tools, methodologies, and specifications across the AI-assisted engineering ecosystem:

### Spec-Driven Development (SDD) Frameworks
- **[Spec Kit](https://github.com/github/spec-kit)** ([spec-kit.dev](https://spec-kit.dev)) — Constitutional Spec-Driven Development toolkit that inspired Architecture Guard's layered constitution model and legacy extension format.
- **[OpenSpec](https://github.com/Fission-AI/OpenSpec)** — Spec-driven change lifecycle (`propose → specs → design → tasks → apply → archive`) supported as a first-class built-in SDD adapter.

### Engineering Methodology & Pragmatism
- **[Ponytail Pragmatism Skill](https://github.com/DietrichGebert/ponytail)** by Dietrich Gebert — Direct inspiration for the **Ponytail Core** contract (`templates/ponytail_core.md`), enforcing an ordered YAGNI decision ladder, root-cause caller tracing, a non-negotiable safety floor, and runnable verification.

### Companion Governance, Memory & Testing Ecosystem
- **[Flash-Mem](https://github.com/DyanGalih/flash-mem)** — SQLite-backed Model Context Protocol (MCP) server for durable project memory, typed knowledge objects, and token-budgeted context retrieval.
- **[Security Review](https://github.com/DyanGalih/security-review)** — Companion whitebox security governance skill suite (`sr-init`, `sr-plan`, `sr-tasks`, `sr-branch`, `sr-audit`, `sr-verify`) for OWASP/CWE verification across plans, tasks, branches, and pull requests.
- **[Spec-Kit E2E Stream](https://github.com/DyanGalih/spec-kit-e2e-stream)** & **[Playwright](https://playwright.dev)** ([`microsoft/playwright`](https://github.com/microsoft/playwright)) — End-to-end UI and API verification patterns powering `ag-e2e-testing`.

### Code Quality & Static Analysis Rule Catalogs
- **[SonarSource Rules Catalog](https://rules.sonarsource.com)** — Upstream rule metadata, severities, and complexity/coupling semantics from **[sonar-java](https://github.com/SonarSource/sonar-java)**, **[SonarJS](https://github.com/SonarSource/SonarJS)**, **[sonar-python](https://github.com/SonarSource/sonar-python)**, and **[sonar-php](https://github.com/SonarSource/sonar-php)** powering the 37 architecture-focused rules in [`sonar-rules/sonarlint-rules.json`](sonar-rules/README.md).

### Backlog, Issue Tracking & Code Host Protocols
- **[Beads (`bd`)](https://github.com/steveyegge/beads)** by Steve Yegge — Distributed, git-backed issue tracker for AI coding agents integrated as a native queue source in `ag-governed-backlog`.
- **[Model Context Protocol (MCP)](https://modelcontextprotocol.io)** & **[GitHub MCP Server](https://github.com/github/github-mcp-server)** — Standardized tool protocol used for Jira story-scope checks, User Story tracker sync, and code-host forge operations.

### Multi-Host Agent & Subagent Runtimes
- **[Claude Code & Agent Teams](https://docs.anthropic.com/en/docs/agents-and-tools/claude-code/overview)** — Native `agteam-*` subagent definitions and experimental team orchestration.
- **[OpenAI Codex CLI](https://github.com/openai/codex)** ([Subagent Configuration](https://learn.chatgpt.com/docs/agent-configuration/subagents)) — Scoped `.codex/agents/agteam-*.toml` role profiles and feature reductions.
- **[Google Antigravity (`agy`)](https://idx.dev)** — Native `.agents/agents/agteam-*.md` subagent invocation and `share` workspace isolation.
- **[OpenCode](https://github.com/sst/opencode)** ([opencode.ai](https://opencode.ai)) — Native `.opencode/agents/agteam-*.md` subagents with declarative read-only tool envelopes.
